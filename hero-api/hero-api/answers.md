## Part 1 — SQL warm-up (Task 1)

```sql
-- 1. Heroes aged 18+, oldest first
SELECT * FROM hero WHERE age >= 18 ORDER BY age DESC;

-- 2. Hero name + team name (heroes without a team included)
SELECT h.name AS hero, t.name AS team
FROM hero h LEFT JOIN team t ON h.team_id = t.id
ORDER BY h.id;

-- 3. Number of heroes per team
SELECT t.name, COUNT(h.id) AS n_heroes
FROM team t LEFT JOIN hero h ON h.team_id = t.id
GROUP BY t.id, t.name ORDER BY t.id;

-- 4. Page 2 with 2 rows per page
SELECT * FROM hero ORDER BY id LIMIT 2 OFFSET 2;
```
Results: (1) Logan 150, Tony 45, Natasha 35. (2) Peter appears with an empty team thanks to `LEFT JOIN` (an `INNER JOIN` would drop him). (3) Avengers 2, X-Men 1 — `COUNT(h.id)` rather than `COUNT(*)`, so a team with no heroes gives 0. (4) Logan (id 3), Peter (id 4).

## Question 1 — Which constraint blocked each statement?

| Statement | Constraint | Why |
|---|---|---|
| `INSERT INTO team ... ('Avengers', 'Los Angeles')` | **UNIQUE** (`team_name_key`) | `name` is `UNIQUE` and "Avengers" already exists. |
| `INSERT INTO hero (name, team_id) VALUES ('Ghost', 99)` | **FOREIGN KEY** (`hero_team_id_fkey`) | There is no team with `id = 99`, so the reference would point to nothing. |
| `INSERT INTO hero (age) VALUES (30)` | **NOT NULL** on `hero.name` | `name` was not given, so it would be NULL. |
| `DELETE FROM team WHERE id = 1` | **FOREIGN KEY** (`hero_team_id_fkey`, seen from the other side) | Tony and Natasha still reference team 1; deleting it would leave orphan rows. |

None of them hit the PRIMARY KEY: `id` is `SERIAL`, so the DB always generates a new value.
Side note: the error message for the third statement shows `Failing row contains (6, ...)` — the failed "Ghost" insert had already consumed id 5 from the sequence. Sequences are not rolled back, so gaps in ids are normal.

## Question 2 — Why is the FK on `hero` and not on `team`?

Each hero belongs to **at most one** team, so a hero row needs only a single value: `team_id`. A team has **many** heroes; to store the FK on `team` you would need a variable number of columns (`hero1_id, hero2_id, ...`) or a list in one cell, which breaks first normal form. Rule: in a one-to-many relationship the FK goes on the "many" side.

## Question 3 — Tables for many-to-many hero ↔ mission

```
hero(id PK, name, age, secret_name, team_id FK → team.id)
mission(id PK, title)
heromissionlink(
    hero_id    INTEGER FK → hero.id,
    mission_id INTEGER FK → mission.id,
    PRIMARY KEY (hero_id, mission_id)   -- composite PK: the same pair cannot appear twice

```
The link table turns one many-to-many relationship into two one-to-many relationships (hero → link, mission → link).

## Question 4 — Why read `DATABASE_URL` from an environment variable?

1. **Security**: the password is not written in the source code, so it does not end up in Git / GitHub (where it is visible to everyone and stays forever in the history).
2. **Same code, different environments**: dev (local Postgres or SQLite), tests, and production each use their own database just by changing the variable — no code changes. This is the "config in the environment" principle of the 12-factor app.
(Bonus: each team member can use their own user/password/port without editing a shared file.)

## Question 5 — Why `id: int | None = Field(default=None, ...)`?

Before it is saved, a Python object has **no id yet**: the id is generated by the database (`SERIAL`) at `INSERT` time. With `int | None` and `default=None` you can create `Hero(name=..., secret_name=...)` without an id; SQLModel leaves `id` out of the `INSERT`, PostgreSQL generates it, and after `commit()` + `refresh()` the object has its real `int` id. The column itself is still `NOT NULL` in the database (it is the primary key).

## Question 6 — Which attributes become columns? What is `back_populates`?

Columns: `id`, `name`, `age`, `secret_name`, `team_id` (plus `power` after Part 9).
**`team` is not a column**: it is a `Relationship()` — a Python-side attribute that SQLAlchemy fills by using the `team_id` FK (it runs a `SELECT` on the `team` table when needed). The same goes for `Team.heroes` and `Hero.missions`.

`back_populates` connects the two ends of the same relationship: `Hero.team` ↔ `Team.heroes`. When you change one side, SQLAlchemy updates the other in memory immediately (e.g. `hero.team = avengers` → `hero` appears in `avengers.heroes` before any commit), and both sides are known to describe the same FK.

## Question 7 — Generated `CREATE TABLE hero` vs the hand-written one

Printed by `echo=True`:
```sql
CREATE TABLE hero (
    name VARCHAR NOT NULL,
    age INTEGER,
    team_id INTEGER,
    id SERIAL NOT NULL,
    secret_name VARCHAR NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY(team_id) REFERENCES team (id)
)
CREATE INDEX ix_hero_name ON hero (name)
CREATE INDEX ix_hero_age ON hero (age)
```
Differences:
- **Column order**: inherited fields from `HeroBase` (`name, age, team_id`) come first, then `id` and `secret_name` from the `Hero` table class.
- **New column** `secret_name VARCHAR NOT NULL` (did not exist in Part 1).
- **Types** are the same: `str` → `VARCHAR`, `int` → `INTEGER`, int PK → `SERIAL`.
- **NOT NULL**: inferred from Python types — `str` (required) → `NOT NULL`; `int | None` → nullable. `id SERIAL NOT NULL` is written explicitly.
- **Constraints**: written as separate table constraints (`PRIMARY KEY (id)`, `FOREIGN KEY(team_id) REFERENCES team (id)`) instead of inline `PRIMARY KEY` / `REFERENCES`. Same effect.
- **Indexes**: extra `CREATE INDEX ix_hero_name` (from `Field(index=True)`), and `ix_hero_age` because I also indexed `age` (it is used by the `min_age` filter). In Part 1 the only index was the one created automatically for the PK. For `team`, `unique=True` + `index=True` becomes `CREATE UNIQUE INDEX ix_team_name` instead of an inline `UNIQUE`.

## Question 8 — Restart: is `CREATE TABLE` printed again?

No. On restart the log shows only checks such as `SELECT pg_catalog.pg_class.relname FROM pg_catalog.pg_class ... WHERE relname = 'hero'`, then no `CREATE TABLE`. `create_all()` uses `checkfirst=True`: for every table in the metadata it asks the database whether the table already exists, and **creates only the missing ones**. It never drops, alters, or compares an existing table — that is why the data survives, and also why it cannot add new columns (Question 17).

## Question 9 — Which line registers `Hero` and `Team`?

```python
from app.models import Hero, HeroCreate, HeroPublic, HeroUpdate, Mission, ..., Team, ...
```
Importing `app.models` executes the class definitions; every `table=True` class adds itself to `SQLModel.metadata` at that moment. If `models.py` were never imported, `SQLModel.metadata` would be empty and `create_all(engine)` would create nothing. (The same reason explains `from app import models  # noqa: F401` in `migrations/env.py`.)

## Question 10 — Without `session.commit()`

- **Response**: `500 Internal Server Error`. `refresh(hero)` raises `InvalidRequestError: Instance '<Hero ...>' is not persistent within this Session`, because the object was never written. (If you also remove `refresh`, the response would fail validation because `id` is still `None`.)
- **Database**: `SELECT * FROM hero;` shows no new row; the session is closed at the end of the request and everything pending is discarded (`ROLLBACK` in the log).
- **`add()` on its own** only puts the object into the session (status *pending*, `id = None`). No SQL is sent. `commit()` flushes (sends the `INSERT`) and commits the transaction.
- **`refresh()`**: after a commit, SQLAlchemy *expires* the object's attributes. `refresh()` runs a `SELECT` to reload the row so the object contains the values generated by the database (the new `id`, and any default values) before we return it as JSON.

## Question 11 — SQL for `PATCH /heroes/1` with `{"age": 17}`

```sql
UPDATE hero SET age=%(age)s::INTEGER WHERE hero.id = %(hero_id)s::INTEGER
-- parameters: {'age': 17, 'hero_id': 1}
```
Only `age` is updated, for two reasons:
1. `hero_in.model_dump(exclude_unset=True)` returns only the fields the client sent → `{"age": 17}`; the other optional fields (`name=None`, ...) are not included, so they are not overwritten with `None`.
2. SQLAlchemy's unit of work tracks which attributes changed on the loaded object ("dirty" attributes) and puts only those columns in the `UPDATE`.

## Question 13 — `GET /heroes?min_age=18&team_id=1`

```sql
SELECT hero.name, hero.age, hero.team_id, hero.id, hero.secret_name
FROM hero
WHERE hero.age >= %(age_1)s::INTEGER AND hero.team_id = %(team_id_1)s::INTEGER
ORDER BY hero.id
LIMIT %(param_1)s::INTEGER OFFSET %(param_2)s::INTEGER
-- [generated in ...] {'age_1': 18, 'team_id_1': 1, 'param_1': 10, 'param_2': 0}
```
The values `18` and `1` **do not appear inside the SQL text**. The SQL has placeholders (`%(age_1)s`), and the values are sent separately in the parameter dictionary (bound parameters). The database receives the query structure and the data separately and always treats parameters as values, never as SQL code. Input like `1; DROP TABLE hero` therefore cannot change the query (here it would be rejected as not-an-int already by FastAPI, and even a string such as `name=' OR 1=1 --` is just matched as text by `ILIKE`).

## Question 14 — Why filter in the database instead of in Python?

`[h for h in session.exec(select(Hero)).all() if h.age >= 18]` loads **every** row from the database, sends it over the network and builds a Python object for each, then throws most of them away.
- **Performance / memory**: with 1 million heroes this is slow and may run out of memory; the database returns only matching rows.
- **Indexes**: the database can use an index (`ix_hero_age`) instead of scanning everything.
- **Pagination is correct**: `OFFSET/LIMIT` must be applied *after* filtering. Filtering in Python after `LIMIT` would return incomplete pages.
- (Also: `h.age >= 18` crashes with `TypeError` when `age` is `None`; SQL handles NULL itself.)
Same idea as in data science: push the computation to where the data is.

## Question 15 — `create_all` created `mission` and `heromissionlink` but did nothing for `hero`. The rule?

`create_all` works **per table, by name**: if a table does not exist → `CREATE TABLE`; if it exists → skip it completely, even if the model has changed. `mission` and `heromissionlink` were new; `hero` already existed. Adding the `missions` relationship did not change the `hero` table itself (a relationship is not a column; the FKs live in the link table), so nothing was needed there anyway.

## Question 16 — Order of `INSERT`s in the seed script

From the `echo=True` log:
1. `INSERT INTO team ...` (Avengers, X-Men) `RETURNING team.id`
2. `INSERT INTO mission ...` (Battle of Sokovia, Stop the Sentinels) `RETURNING mission.id`
3. `INSERT INTO hero ...` — with parameters `team_id__0: 1, ...`
4. `INSERT INTO heromissionlink (hero_id, mission_id) VALUES ...` — `[{'hero_id': 4, 'mission_id': 2}, {'hero_id': 2, 'mission_id': 1}, ...]`

At `commit()`, the session's unit of work sorts the pending objects by their **dependencies (FKs)**: a parent must exist before a row that references it. So `team` and `mission` go first; their generated ids are read back with `RETURNING id`. SQLAlchemy then copies `avengers.id` into `hero.team_id` (because of the relationship `team=avengers` and its FK), inserts heroes, and finally inserts the link rows using the hero and mission ids it now knows. We never typed an id.

## Question 17 — Added `power`, restarted. Is there a `power` column?

No. `\d hero` shows no `power` column, because `create_all` skips existing tables (Q8/Q15).
`GET /heroes` → **500 Internal Server Error**:
`psycopg.errors.UndefinedColumn: column hero.power does not exist`. The model now says that `hero` has `power`, so SQLAlchemy generates `SELECT hero.name, ..., hero.power ... FROM hero`, but the real table does not have that column: the Python model and the database schema are out of sync.

"Drop all tables and run `create_all` again" is not acceptable in production because it **deletes all the data** (real users, orders...). You need to change the schema *in place* while keeping the rows (`ALTER TABLE hero ADD COLUMN power VARCHAR`), in a controlled, repeatable, reversible way on every environment (dev, teammates, staging, prod) — which is what migrations do.

## Question 18 — Body of the generated migration

```python
def upgrade() -> None:
    op.add_column('hero', sa.Column('power', sqlmodel.sql.sqltypes.AutoString(), nullable=True))

def downgrade() -> None:
    op.drop_column('hero', 'power')
```
- `upgrade()` adds a nullable `power` column (`AutoString` = `VARCHAR`) to `hero` → `ALTER TABLE hero ADD COLUMN power VARCHAR`. Existing rows keep their data and get `NULL`. It is nullable because the field is `str | None` — adding a `NOT NULL` column without a default would fail on a non-empty table.
- `downgrade()` is the exact reverse: `ALTER TABLE hero DROP COLUMN power` (the values in that column are lost).
- `sqlmodel.sql.sqltypes.AutoString` is the reason we added `import sqlmodel` to `script.py.mako`; without it the migration file would crash with `NameError`.

Verified: after `upgrade head` `\d hero` shows `power`; after `downgrade -1` it is gone; after `upgrade head` it is back. Then `PATCH /heroes/1 {"power": "flight"}` → `200`, and `GET /heroes` works again and returns `power`.

Note on my repo: before this revision I created a baseline revision **`initial schema`** (autogenerated against an empty database, it creates the 4 tables) and ran `alembic stamp head` on my existing database, which already had these tables. Without it, the history would start with "add hero.power", and a teammate with an empty database (Checkpoint 10) would get `relation "hero" does not exist` on `alembic upgrade head`. History:
```
5ee65f229273 -> b1f846ba0798 (head), add hero.power
<base> -> 5ee65f229273, initial schema
```

## Question 19 — Where does Alembic store the current revision? Why commit `migrations/`?

In a table **`alembic_version`** in the database itself (visible in `\dt`), with a single column `version_num`. Here: `b1f846ba0798`. `alembic current` reads this table; `upgrade` runs every revision after it and then updates it.

`migrations/` must be in Git because the migration files **are the history of the schema**, as code: every teammate, the CI and the production server run the same `alembic upgrade head` and get exactly the same schema, in the same order. The schema changes are reviewed together with the code that needs them (the `power` field and the migration are in the same commit), and you can go back to an older version (`downgrade`). If the files were not committed, other databases could not be upgraded, and a database whose `alembic_version` points to a revision file that nobody has would be stuck.

## Question 20 — Renaming `secret_name` → `alias` with autogenerate

Generated:
```python
def upgrade() -> None:
    op.add_column('hero', sa.Column('alias', sqlmodel.sql.sqltypes.AutoString(), nullable=False))
    op.drop_column('hero', 'secret_name')

def downgrade() -> None:
    op.add_column('hero', sa.Column('secret_name', sa.VARCHAR(), autoincrement=False, nullable=False))
    op.drop_column('hero', 'alias')
```
Autogenerate only compares the model with the database: it sees "column `alias` is missing" and "column `secret_name` is extra". It cannot know that this is a rename, so it generates **add new + drop old**.

Why it is dangerous:
1. `drop_column('secret_name')` **destroys all the secret names**; `alias` would not contain them.
2. Adding `alias` as `NOT NULL` with no default fails on a table that already has rows (`column "alias" contains null values`), so on real data the migration does not even run. On an empty dev DB it works, which hides the problem until production.

Fix — edit the script by hand to use a real rename, which keeps the data:
```python
def upgrade() -> None:
    op.alter_column('hero', 'secret_name', new_column_name='alias')

def downgrade() -> None:
    op.alter_column('hero', 'alias', new_column_name='secret_name')
```
(If the change were more complex than a rename: add the new column as nullable → `op.execute("UPDATE hero SET alias = secret_name")` → set it `NOT NULL` → drop the old column.)

Afterwards I deleted the revision file and undid the rename; `alembic check` reports `No new upgrade operations detected.`

## Review questions

1. **Primary key**: uniquely identifies each row (unique + not null); other tables reference it with FKs.
2. **ORM benefit**: work with Python classes/objects instead of writing SQL strings: types, validation, relationships as attributes, safe parameterised queries, and portability between databases (SQLite ↔ PostgreSQL).
3. **`table=True`**: the class becomes a database table (it is registered in `SQLModel.metadata`, has columns, can be used in `select`/`session`); without it the class is only a Pydantic schema.
4. **`session.commit()`** saves the data (`add()` only stages it).
5. A **list of model instances** (e.g. `list[Hero]`), possibly empty.
6. **Alembic**: versioned, reversible migrations of the database schema (change tables without losing data, same schema on every machine).
7. `create_all` only creates **missing tables**; it never alters an existing table, so a new column needs a migration.
8. On the **"many" side**: `hero.team_id` → `team.id`.
